01结论摘要

不是同一层的东西

Codex 是产品化编码代理（CLI + IDE + 云 + 移动）；DSH 是可编程 agent 宿主/编排内核（多客户端、多模型、插件可改宿主组合）。

Codex 的护城河在工程深度

三平台原生沙箱 + 保护区路径 + 网络默认关闭与白名单代理 + granular 审批 + auto_review 自动审批者 + 成熟的 CI 协议（exec --json / --output-schema / app-server）。

DSH 的护城河在开放边界

全栈 MIT，连组合层（bundle 栈 + patch 层）都开放；模型/客户端可换；沙箱 fail-closed；隐私默认更保守（遥测反馈门控）。

Codex 已不是"只有 CLI"

app-server（JSON-RPC 2.0，thread/turn/item）是正式嵌入协议，TUI 可用 --remote ws:// 远程接管；子代理默认开启。

DSH 的编排形状更丰富

subagent / workflow（JS 扇出 + 阶段 + JSON Schema）/ ralph（fresh-agent 轮次）/ goal（跨轮目标）。

组合比替代更现实

DSH 能把 Codex 当子代理跑（packages/subagent/subagent-codex），也有兼容其 hook 协议的 hooks-codex。

02对初版判断的三处更正

初版对比基于本机命令表与既有印象，本轮以官方文档复核后，以下三条判断被推翻或修正。保留在此以便追溯证据变化。
初版说法复核后的事实影响
"Codex 无通用多代理编排原语" 错误。子代理默认开启（agents.enabled），内建 default/worker/explorer，有 agents.max_concurrent_threads_per_session、/agent 切线程、Ultra 模式主动委派、自定义 agent TOML；另有云并行任务与 git worktree。（官方文档） 编排差距比初版描述的小。DSH 仍胜在编排形状（workflow/ralph/goal），而非"有没有子代理"。
"靠 codex mcp-server 反向暴露给其它 agent" 已过时。app-server（双向 JSON-RPC 2.0，thread/turn/item，stdio/WebSocket/Unix socket）成为正式嵌入协议，mcp-server 已被移除。本机 0.121.0 仍列该子命令，属版本差异。（本机 官方文档） Codex 的可嵌入性高于初版评价。
"Codex 是应用、DSH 是平台" 需修正。Codex 现在也暴露内核协议（codex app-server --listen ws://… + codex --remote ws://…）。真正的差异是开放边界的宽度，不是"有没有内核"。 定位表述改为：同为"内核 + 多客户端"，开放面与编排层厚度不同。

06优劣势对照

DSH 优势

  • 模型自由：换 provider / 中转站 / 本地模型不动宿主
  • 可编程到骨头：插件能改宿主组合，而非只挂工具
  • 多客户端同源：Web / TUI / Desktop / 编辑器 / SDK 共用一个会话内核
  • 编排形状丰富：subagent / workflow / ralph / goal
  • 沙箱 fail-closed + 执行强度上报，可接 E2B 云沙箱
  • 隐私默认保守（遥测反馈门控）、中文一等公民、全栈 MIT
  • 会话格式有版本契约

DSH 短板

  • 上手重：Node + pnpm + profile/bundle 概念，rc 阶段
  • 审批仅两档，无自动审批者、无保护区路径、无网络白名单代理
  • 无官方云执行/托管（E2B 需自配密钥且默认关闭）
  • 生态年轻，第三方插件质量与安全需自行评估
  • 未见企业策略强制层（未穷尽核实）

Codex 优势

  • 开箱即用：装完登录即可干活，心智负担低
  • 沙箱工程最深：三平台原生后端、保护区路径、网络默认关 + 白名单代理、独立 codex sandbox
  • 审批最细：granular 子策略 + auto_review 自动审批者
  • CI 协议成熟：exec --json / --output-schema / app-server
  • 产品面广：TUI / IDE / 桌面 / 云 / 移动 / PR 评审一体化
  • 零依赖单二进制（musl 静态），启动快
  • 企业治理：requirements.toml + MDM + workload identity

Codex 短板

  • 模型绑定倾向明显：云模型不可换，第三方须 responses API，模型退役频繁
  • 关键层闭源：IDE 扩展、Cloud、模型；Cloud 无法自托管
  • 匿名遥测默认开、transcript 默认落盘
  • 成本不透明：额度与 ChatGPT 共享，usage API 需登录态
  • 已知持久化缺陷：rollout 错误在 resume/fork 时被静默丢弃
  • hooks 非完整强制边界；网络代理不覆盖搜索/MCP/浏览器/云

07选型矩阵

场景推荐理由
个人/小团队快速写代码，追求稳定Codex登录即用，TUI 手感成熟，沙箱/审批默认值安全

08风险与已知缺陷

对象问题证据强度
Codexrollout 持久化错误在 resume/fork 时被静默丢弃（core/src/session/mod.rs），崩溃后可能截断官方仓库源码
CodexWindows / side-chat 的 "duplicate rollout ordinal" 缺陷（issues #35385 / #42157 / #42027 / #43142）官方议题
Codexhooks 不是完整强制边界；network_proxy 仅覆盖沙箱内命令流量，不含 web search / MCP / apps / browser / cloud第三方实测
Codex成本不透明：Codex 与 ChatGPT 共享额度；usage / rate-limit API 需 ChatGPT 登录态官方文档
Codex上下文窗口缩水争议（第三方追踪称 372k→272k、超额静默计费）——原文未取到，数字未核实未核实
Codex文档自相矛盾：Approvals 页仍列 unless-trusted/on-failure，config 参考称已退役/弃用官方文档冲突
DSHrc 阶段（0.1.5-rc.2）：插件 API 与客户端行为可能仍有不兼容变更本机
DSH审批只有 ask/never，无 granular 子策略与自动审批者本机源码
DSH无保护路径（.git 等）与网络白名单代理；沙箱依赖平台后端可用性本机源码
DSH第三方插件高权限（读会话日志、经凭据 seam 读 key、网络），收录不等于背书插件文档

09未能核实的事项

  • Codex cloud / app-server / exec-server 的稳定契约（官方仍标 experimental，相关博客返回 403）
  • unless-trusted / on-failure 在本机 0.121.0 二进制中是否仍可用（文档自相矛盾）
  • Codex IDE 扩展内部是否直连 app-server；codex plugin / marketplace 的包格式细节
  • Codex rollout JSONL 的稳定性（hooks 文档明确称其非稳定接口）
  • DSH 是否在别处存在等价于 requirements.toml 的企业策略层（未穷尽检索）
  • Codex Rust 测试体系与 DSH 质量工程的等价性比较（未做逐项对照）
